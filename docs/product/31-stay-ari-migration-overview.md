## 무엇을 왜 하는가

지금 업무가 **웹 두 개에 나뉘어** 있다. Foldy(현장 운영)와 STAY ARI Manager(가격·매출·자동화).
이 이전의 목적은 **하나의 웹에서 모든 업무를 하는 것**이다. 이전이 끝나면 저쪽 웹은 폐지한다.

단순 복사가 아니다. 목적이 셋이다.

1. **합친다** — 두 웹을 오가지 않는다.
2. **고친다** — 저쪽에서 아쉬웠던 부분을 그대로 옮기지 않고 개선한다.
3. **모바일에서 쓴다** — 아래 참고. 이번 이전에서 **가장 중요한 요구**다.

### 모바일이 설계의 출발점이다

저쪽 웹은 PWA 이지만 **모바일이 제대로 구현돼 있지 않다.** 사실상 PC 에서만 쓴다.

Foldy 로 옮기면서 **읽기와 쓰기 모두 모바일에서 가능해야 한다.** 「누워서도, 어디서도」가
요구사항 그대로다. 이것은 부가 조건이 아니라 **기능 설계의 제약**이다 —

저쪽 캘린더의 핵심 상호작용은 **마우스 드래그**로 기간을 고르는 방식이다
(`handleCalendarMouseDown → MouseMove → MouseUp`). 손가락으로는 스크롤과 충돌하고, 좁은 화면에서
30일 × 26객실을 드래그하는 것은 실용적이지 않다. **그대로 옮길 수 없다.** 입력 방식을 새로
설계한다 → [33-calendar-write-features.md](33-calendar-write-features.md)

## 이식 원칙 — 항상 「읽고 → 개선해서 → 짓는다」 (확정, 2026-10-01 사용자 지시)

모든 이식 작업은 이 순서를 지킨다. 예외 없다.

1. **저쪽 구조와 설계를 먼저 읽는다.** 화면 하나, 계산 하나를 옮기더라도 저쪽 원본
   (`/mnt/c/-stay-ari-manager-main`)에서 그 기능의 구조 · 데이터 흐름 · 규칙 · 예외 처리를 끝까지 읽는다.
   기억이나 추측으로 다시 만들지 않는다. 읽은 내용(파일 · 함수 · 규칙)은 해당 문서에 출처와 함께 남긴다
   (예: 34번 「지표 정의 — 저쪽 코드에서 읽은 그대로」, 33번 「저쪽 설계 — 읽어낸 내용」).
2. **우리 쪽에 맞게 업그레이드한다.** 그대로 복사하지 않는다 — 저쪽에서 아쉬웠던 점(모바일 · 속도 · 화면 복잡도 ·
   틀린 규칙 · 하드코딩 · 중복 계산)을 고치고, Foldy 계약(다국어 ko/ja/en · 조직 격리 · 서버 권한 · 도쿄 날짜 ·
   공용 콘솔 부품 · 실시간 웹훅)에 맞춰 다시 설계한다.
3. **무엇을 그대로 두고 무엇을 바꿨는지 적는다.** 숫자가 걸린 것은 기본이 「저쪽 그대로 재현」이다(2026-09-30
   결정) — 바꾸면 이유와 저쪽 값을 함께 적고, 사용자 확인을 받는다(예: 매출 요약 여러 건물 ADR).
4. **원본과 대조해 검증한다.** 같은 입력 · 같은 기간으로 저쪽(또는 Beds24 원본)과 숫자를 맞춘다.

## 저쪽 프로젝트의 형태

| | |

짓는다.** 저쪽 코드는 「무엇을 어떤 규칙으로 하는가」의 참고 자료로만 쓴다.

> 고치고 Beds24 에 나간다(되읽기 검증·전송 로그로 확인). 저쪽 웹도 아직 살아 있어서 **같은 Beds24 를 두 곳에서
> 고칠 수 있는 상태**다 — 서로 덮는 것은 Beds24 가 마지막 값을 가지므로 데이터 손상은 아니지만, 같은 날짜를 두 곳에서
> 동시에 만지지 않도록 저쪽 캘린더의 가격 수정은 쓰지 않는 것을 원칙으로 한다. 자동화(Slack·노션)는 여전히 저쪽만
> 보낸다 — 이쪽은 아직 만들지 않았다.
>
> **2026-10-06 (사용자)**: **저쪽 프로젝트 자체를 멈췄다** — Slack 자동화 · Beds24 API 연결 · Hotelsmart 자동 수집 · 구글 시트 · Notion ·
> 전표 스냅샷 등 스케줄 전부. (Firestore 데이터는 남아 있다 — 전표 과거분 · 룸 링크 등 이관이 끝날 때까지 **지우지 않는다**.) → 같은 Beds24 를 두 곳에서 고치는
> 문제와 Slack 이중 발송 위험은 사라졌다. 대신 **지금은 Slack 리포트(일일 · 청소 명단 · 취소 · 당일예약 · 실패 알림)가 어디서도
> 나가지 않는 공백 상태**다 — 자동화 이식(36번)이 급하다. 저쪽 Firestore 데이터(전표 스냅샷 포함)는 이 날짜로 멈춘다.

대신 하나가 생긴다 — **켜기 전에 어떻게 검증하는가.** 실제로 쓰거나 보내보지 않고는 확신할 수
없기 때문이다. 각 문서의 「전환 전 검증」 절이 이 문제를 다룬다.

### 전환(cutover)의 단위

기능 단위로 끊어서 넘긴다. **한 번에 전부 넘기지 않는다** — 되돌릴 구간이 없어진다.

```
① 읽기 (가동률·매출)  → 위험 없음. 숫자가 저쪽과 맞는지만 대조한다.
② 자동화              → 이쪽을 켜는 순간 저쪽 스케줄을 끈다. 한 쌍으로 움직인다.
③ 캘린더 (쓰기)       → 마지막. 그 전까지 데이터 정합성을 충분히 본다.
```

**왜 이 순서인가**: 읽기는 틀려도 화면 숫자가 이상할 뿐이지만, 쓰기는 틀리면 에어비앤비·
부킹닷컴에 그대로 나간다. 읽기로 데이터가 맞다는 것을 먼저 확인하고, 그 확신 위에서 쓰기를
켠다.

아래가 **전부** 충족되면 폐지한다. 하나라도 빠지면 유지한다.

- [ ] 4개 영역이 Foldy 에서 동작한다
- [ ] 가동률·매출 숫자가 저쪽과 **한 달치 이상 일치**한다
- [ ] 자동화 13종이 이쪽에서 발송되고, 저쪽 스케줄이 꺼져 있다 (저쪽 Slack · Beds24 연결은 2026-10-06 중단 — 이쪽 발송이 남음)
- [x] 캘린더 쓰기가 실제 Beds24 에 반영되는 것을 확인했다 (2026-09-24~, 되읽기 검증 · 전송 로그)
