## 1. 하려는 것

손님 메시지가 오면, **뜻이 비슷한 과거 질문과 그때 우리가 보낸 답장**을 DB 에서 찾아서

1. 맞는 「정해 둔 문구」를 추천하고 (아이디어 1)
2. 과거 답장을 참고한 **답장 초안**을 손님 언어로 만들어 준다 (아이디어 2)

**사람이 보고 보낸다.** 자동으로 나가는 답은 이 단계에 없다(건물 안내 노트 기반 자동 답은 아이디어 3, 다음 단계).

## 3. 흐름 (안)

```
손님 메시지 도착
 → 걸러내기: 인사 · 사진만 · 시스템 → 「답 필요 없음」 표시, 끝
 → 뜻 숫자로 바꾸기(임베딩) → DB 에 저장
 → 같은 건물 우선 + 최근 12개월 우선으로 비슷한 과거 질문 5~10개 찾기
 → 정해 둔 문구 중 맞는 것 1~3개 추천
 → (버튼 누르면) 과거 답 + 정해 둔 문구 + 예약 정보로 답장 초안, 손님 언어로
 → 직원이 고쳐서 보냄
```

- 과거 메시지 2.2만 묶음은 처음 한 번 숫자로 바꿔 둔다(1회 비용 수천 원 수준, 실제 값은 시작 전에 계산).
- 새 메시지는 도착할 때마다 하나씩 바꾼다.

## 4. 지켜야 할 것

- **출입 코드 · 비밀번호는 가리지 않는다** (2026-11-17 사용자 결정 — 건물 고정 값이라 그대로 써야 답이 됨).
- 비밀번호는 **방마다 고정**(48 §8-4). 초안의 번호는 **지금 예약의 방에 저장된 손님용 번호**에서만 가져온다
  (다른 방 손님 대화의 번호를 옮기지 않음). 아라키초 B 는 손님용 · 현장용 2개 — 손님용만. 창고 · 직원 키박스 등
  **직원용 번호는 초안에 절대 넣지 않는다.**
- 손님 쪽 개인정보(다른 손님 이름 · 전화번호 · 메일 · 여권)는 초안에 옮기지 않는다.
- 취소 · 환불 · 결제 · 수리비 청구 · 날짜 변경 · 연장 · 인원 변경 · 소음 · 보안 · 고장 · 시설 불편 · 청결 불만 · 분실물은 **초안을 만들어도 「사람 판단 필요」 표시**를 단다.
- **정책표는 기본값일 뿐이다(2026-11-17 사용자).** 변수(다음 손님 · 청소 일정 · 방 상태 · 손님 사정)로 어느 날은 달라질 수 있다. 초안은 기본값으로 쓰되 단정하지 않고, 그날 사정에 달린 주제(늦은 체크아웃 · 이른 체크인 · 짐 · 방 이동 · 무료 요청)는 「확인 필요」 + 「사람 판단 필요」를 단다. 무료는 규칙으로 두지 않는다(48 §8-9 결정 2).
- 조직마다 따로(다른 조직 대화가 검색되면 안 됨) — 서버에서 조직으로 거른다.
- 비용 상한 · 하루 사용량 기록. 실패하면 메시지함은 그대로 쓸 수 있어야 함(도우미만 안 뜸).
- 화면 문구는 ko · ja · en 같이. 모바일은 폰 · 폴드 · 태블릿, PC 메시지함도 같이.

**덧붙인 결정(2026-11-17)**

- **비밀번호 · 와이파이 값은 AI 가 쓰지 않는다.** 초안에는 자리 표시만 두고 그 예약의 방 정보에서 시스템이 채운다(다른 방 값이 섞이는 위험 차단). 코드 볼 권한이 없는 사람에게는 지금처럼 가려 보인다.
- **초안을 만들지 않는 경우**: 답이 필요 없는 메시지(시험 23%)와 그 예약만의 사정이 걸린 질문(시험 26%)은 초안 대신 「직접 확인이 필요해요」.
- **비용**: Sonnet 5.5 기준 초안 하나 약 $0.01, 하루 50건이면 한 달 약 $15. 한 달 상한을 두고 넘으면 초안 버튼만 멈춘다(문구 추천은 계속).

## 7. 미리 시험 결과 (2026-11-17)

**방법**
- 재료: 운영 DB에서 읽기만 해서 최근 1년 질문 → 답 묶음 14,621개를 만들었다(사진만 있는 메시지 · 15자 미만 메시지 제외).
- 변환: Voyage `voyage-4`, 48만 토큰(무료 범위 안).
- Voyage 계정은 학습 사용 끄기(Opted Out, 보낸 데이터 바로 삭제) · 월 사용 한도를 걸어 두었다.
- 시험: 최근 30일 질문 400개를 무작위로 골라, **그 이전** 같은 조직 대화 12,787개에서 뜻이 가장 비슷한 과거 질문 3개와 그때 보낸 답을 찾았다(같은 건물이면 조금 더 위로).
- 판정: 에이전트 4개가 100개씩 「찾은 답이 초안 바탕으로 쓸 만한가」를 읽고 판정했다.
- 시험 자료(원문 · 변환 값)는 끝난 뒤 지웠다.

**위험한 경우 (그대로 쓰면 틀림)**
- 과거 답에 **다른 방의 와이파이 · 출입 코드 · 방 번호 · 사전 등록 링크**가 들어 있다.
- 같은 질문에도 과거 답끼리 정책이 서로 다르다.
  - 늦은 체크아웃 요금: 무료 · 2,000 · 4,000 · 6,000 · 8,000엔
  - 체크아웃 뒤 짐: 맡아 준다 / 안 맡는다 / 코인 로커
  - 세탁기: 건조 됨 / 안 됨
- 건물마다 다른 사실(엘리베이터 · 주소 · 짐 두는 곳)이 다른 건물 답에서 따라온다.
- 「방 준비됐어요 / 아직이에요」 같은 그날 상태 답이 다른 날로 옮겨 온다.
- 여러 부분으로 된 질문은 한 부분만 찾는다.
- 「확인해 볼게요」 같은 내용 없는 답이 위로 올라온다.

**설계에 주는 뜻**
1. **과거 답은 「말투 · 구성」 참고로만 쓰고, 사실(코드 · 요금 · 정책 · 시설)은 가져오지 않는다.**
   - 사실의 출처는 지금 예약의 방 값과 건물 안내 노트(`property_operation_infos`), 그리고 정해 둔 문구뿐이다.
   - 따라서 **건물별 안내 노트를 채우고, 늦은 체크아웃 등 정책을 한곳에 정리하는 일이 먼저**다(48 §8-7 자동 메시지 모순도 함께).
2. 과거 답에서 코드 · 방 번호 · 링크 · 전화번호 · 금액을 지운 뒤에 초안 모델에 넘긴다.
3. 「답 필요 없음」(23%)은 도착 때 AI 표시로 거른다. 검색하지 않는다.
4. 「이 예약에만 해당」(26%)은 초안에 「확인 필요」 칸을 남기고 「사람 판단 필요」 표시를 단다.
5. 화면은 1순위 하나가 아니라 **비슷한 과거 대화 3개를 보여 주고 사람이 고르게** 한다.
6. 검색 품질 자체는 충분하다. 여러 언어(한 · 중 · 일 → 영어 답)도 같은 뜻으로 잘 찾았다. 그러니 임베딩 방식은 그대로 간다.

## 8. 기술 설계 (2026-11-18)

**초안 언어 결정(2026-11-18 사용자 — 추천안)**: 초안은 **보는 직원 언어**로 쓴다. 손님에게는 지금 있는 「손님 언어로 번역해서 보내기」로 나간다
(직원이 읽고 고치기 쉬움). §1 · §3 의 「손님 언어로」는 이 결정으로 바뀐다.

| `guest_reply_assist_events` | 도우미 기록 하나 | `organization_id` · `conversation_id` · `user_id` · `kind`(`pending` · `draft` · `direct` · `failed` · `wrong` · `sent_as_is` · `sent_edited` · `discarded`) · `draft_id`(같은 초안 묶음) · `message_id`(가리킨 손님 메시지) · `model` · `input_tokens` · `output_tokens` · `cost_micro_usd` · `wrong_reason` · `draft_hash`(채운 초안 sha256 — 글은 안 남김) · `placeholders`(남은 자리 표시 글) · `created_at` |

- 세 테이블 모두 RLS 켬 · 정책 없음 · `service_role` 만 GRANT(손님 메시지 표와 같은 방식 — 서버 액션이 세션 조직 · 권한을 본 뒤 읽음).
- `vector` 확장(`extensions` 스키마) · `guest_reply_pairs.embedding` HNSW(코사인) 색인.
- 검색 함수 `guest_reply_similar(p_organization_id, p_embedding, p_property_name, p_since, p_before, p_limit)` — security invoker · `service_role` 만 실행.
  같은 건물이면 거리에서 조금 뺀다(0.03). 기본 최근 12개월(D4, 도쿄 날짜 기준 N달 전 자정).
  그 조직 · 기간 · 답 있는 줄이 5,000개 이하면 **색인 없이 전부 정확히** 계산한다(조건으로 걸러 후보가 모자라는 일이 없게).
  그보다 많으면 색인으로 가까운 60개를 뽑고 그 안에서 순위를 다시 매긴다 — `hnsw.ef_search = 100` · `hnsw.iterative_scan = relaxed_order`
  (pgvector 0.8+, 걸러져 모자라면 색인을 더 읽는다). 로컬 pgvector 0.8.1 에서 두 길 모두 실행 확인.
- 한 초안에 처음 기록(`pending` → `draft` · `direct` · `failed`) 하나 · 끝 기록(`sent_as_is` · `sent_edited` · `discarded`) 하나(부분 고유 색인). `wrong` 은 여러 번.
- 비용 합 함수 `guest_reply_assist_cost_since(p_since)` — **모든 조직 합**(Anthropic 키 하나를 같이 쓴다, DeepL 한도와 같은 방식). `service_role` 만.
- 한도 잡기 함수 `guest_reply_assist_reserve(…, p_cap_micro_usd, p_reserve_micro_usd)` — 잠금(`pg_advisory_xact_lock`) 하나 안에서 이번 달 합 +
  이번 몫(0.04달러)이 한도를 넘으면 `false`, 아니면 `pending` 줄을 넣고 `true`. 부른 뒤 서버가 같은 줄을 실제 결과 · 비용
  (`draft` · `direct` · `failed`)으로 바꾼다 — 동시에 여러 번 눌러도 한도를 넘지 않는다. `service_role` 만.

### 8-2. 흐름

1. **대화를 열면**(답장 권한 있는 사람만) `getReplyAssist(conversationId)`:
   마지막 손님 메시지가 「답 필요 없음」(15자 미만 · 사진만 · 시스템)이거나 **그 뒤에 우리 답이 이미 있으면** `{ kind: "none" }`.
   아니면 그 글을 숫자로 바꿔(이미 바꿔 둔 게 있으면 재사용 — `guest_reply_pairs` 에 질문 줄로 저장) 정해 둔 문구 1~3개(유사도 0.55 이상) + 비슷한 과거 대화 3개를 돌려준다.
   Voyage 키가 없거나 실패하면 `{ kind: "unavailable" }` — 화면은 도우미 줄만 숨긴다(메시지함은 그대로).
2. **「초안 만들기」** → `draftGuestReply(conversationId)`:
   답장을 받지 않는 채널(직접 예약 · 모르는 채널, `replyBlockReason`)이면 외부 호출 전에 `forbidden`(개요는 `unavailable`).
   한도 잡기(`pending`) → Claude 로 초안 → 같은 줄을 `draft` 로 정산 → `{ draftId, text, lang, checks[], needsHuman, reason, placeholders[] }`.
   그 예약에만 해당하는 질문이면 초안 없이 `direct`. 답할 질문이 없으면 `invalid`. `needsHuman` 은 모델 값 **또는** 서버 주제 검사(취소 · 환불 ·
   늦은 체크아웃 등 ko/ja/en/zh 낱말) — 모델이 놓쳐도 켜진다. 모델 `reason` 글에도 이 건물 코드가 나오면 가린다.
   모델이 거절 · 잘림 · 모양 틀림으로 실패해도 쓴 토큰 · 비용은 `failed` 로 남는다(요금은 나가므로 한도에 센다).
3. **보낼 때** `sendGuestReply({ …, assistDraftId })` — 서버가 **`assistDraftId` 가 없어도 늘** 먼저 **직원 원문(`original`)과 보낼 글(`body`) 둘 다**에서
   채우지 않은 자리 표시(세 언어 자리 표시 전부 + 날것 `{entry_code_room}` · `{wifi}` + 있으면 그 초안의 것)를 찾아 있으면 `assist_placeholder` 로
   거절한다(큐에 안 넣음) — 다시 만들기가 실패해 옛 초안이 칸에 남은 채 보내는 경우도 막는다.
   보낸 뒤(`after()`, 실패는 삼킴) 초안 해시와 비교해 `sent_as_is` / `sent_edited` 를 기록(공백 차이는 같은 글).
   도우미가 켜진 환경(Voyage 키 있음)이면 보낸 답(가리기 뒤)을 **보내기 직전 대화의 마지막 질문 하나**(답 없음 · 12시간 안)에만 붙인다 —
   다음 검색 재료. 규칙은 개요의 질문 고르기 · 백필 짝 맞추기와 같다: 질문과 답 사이에 다른 손님 질문이 오면 앞 질문은 답 없음.
   다시 만들기 · 답장 칸 비우기 = `discarded`. 「틀렸어요」 = `wrong`(+ 이유 하나).

### 8-3. 초안에 넘기는 것 · 넘기지 않는 것

- 넘김: 최근 대화 12줄(코드 가림) · 예약 기본(건물 · 방 · 날짜 · 인원 · 채널) · 건물 안내 노트(손님용 칸, 코드 · 와이파이 비밀번호 칸 제외) ·
  맞는 정해 둔 문구 · 비슷한 과거 답 3개(**가리기 뒤**).
- 과거 답 가리기: 출입 코드 · **와이파이 이름 · 비밀번호**(건물 손님용 칸 값) · 3자리 이상 숫자 묶음 · 방 번호 · URL · 메일 · 전화번호 · 금액(¥ · 엔 · 円) → `[…]`. 말투 · 구성 참고용(§7 설계 1).
- **비밀번호 · 와이파이 값은 모델에 주지 않는다.** 모델은 `{entry_code_room}` · `{wifi}` 자리 표시만 쓴다. 서버가 돌려주기 전에
  출입 코드를 볼 수 있는 사람(`canSeeStaffCodes` 와 같은 규칙)이면 **지금 예약의 방 손님용 코드**로 채우고, 아니면 자리 표시
  (「[출입 비밀번호]」, 보는 사람 언어)를 남긴다 — 자리 표시가 남아 있으면 보내기를 막는다.
  - 코드 고르기(`guestEntryCodeFor`): 그 방의 `room_access` 번호 → 없으면(건물에 방 번호가 하나도 없을 때만) 손님용 공용 번호
    (`roomPassword` · `doorPassword`)가 **딱 하나**일 때 그것 → 아니면 자리 표시. 창고 · 키 박스 · 리넨실 번호는 절대 넣지 않는다.
  - 와이파이는 건물 손님용 칸 값으로 채운다(답장 칸 넣기 목록과 같은 꼴, 보는 직원 언어).
  - 지킴 한 번 더: 모델 글에 이 건물 코드 값이 나오면 채우기 전에 `{entry_code_room}` 로, 와이파이 값이 나오면 `{wifi}` 로 되돌린다.
  - `{wifi}` 는 **이름표까지 붙은 한 줄**(「와이파이: … / 비밀번호: …」)로 채워진다. 지시문에 「앞에 이름표를 붙이지 말 것」을 적고, 그래도
    줄 맨 앞에 「Wi-Fi:」 · 「와이파이 정보:」 · 「Wi-Fi情報：」 같은 이름표를 붙였으면 서버가 떼고 채운다(`stripWifiLabelBeforeToken`).
  - 가릴 값 목록(`secretsOf` = 출입 코드 + 와이파이 이름 · 비밀번호)은 질문 줄 저장 · 보낸 답 붙이기 · 백필 · 모델 입력(대화 · 질문 · 건물 노트) ·
    모델 출력(`checks` · `reason`) · 비슷한 대화 내보내기(읽을 때 그 줄 건물 값으로 한 번 더) 모두 같은 목록을 쓴다.
- 출력은 **structured output**(`output_config.format` JSON 스키마 — 강제 도구 호출은 생각(thinking)과 같이 못 써서): `kind`(`draft` · `direct`) ·
  `text` · `checks`(확인 필요 문구, 최대 4 — 서버가 초안 안 정확한 부분 문자열만 남김) · `needsHuman`(§4 주제) · `reason`.
- 질문 줄은 같은 메시지 · 같은 모델 숫자가 이미 있으면 다시 바꾸지도 쓰지도 않는다. 가짜 모드 숫자는 `embed_model = "fake"` 로 적어, 진짜 키로 돌리면 다시 바꾼다.
- 질문 줄을 저장할 때도 출입 코드 · 그 손님 이름 · 연락처(URL · 메일 · 전화)를 가린다. 초안 글 자체는 DB 에 남기지 않는다.

### 9-1. 지키는 것

- **사람이 「추가」 · 「넣기」를 누르기 전에는 아무것도 저장하지 않는다.** 뽑기는 후보 표 · 실행 표에만 쓴다(시험이 쓰기 표 목록을 고정).
- **출입 비밀번호 · 와이파이 비밀번호 · 문 코드는 절대 뽑지 않는다** — 세 겹:
  1. 모델에 주는 답장은 가린 뒤의 글(`maskPastReply` — 조직 전체 코드 + 그 건물 코드 · 와이파이 값 · 숫자 3자리 이상 · 이름 · 연락처 → `[…]`).
     띄어쓰기 · 하이픈으로 나눠 쓴 숫자(`1 2 3 4` · `12-34`)는 **비밀 낱말(와이파이 포함)이 든 문장 안에서만** 가린다 —
     「Check-in 15:00-22:00」 · 「10-15 minutes walk」 · 「徒歩10分」 같은 시간 · 거리는 남긴다. 이 가림은 AI 초안(§8)의 지난 답장에도 같이 쓴다.
  2. 지시문에 「비밀번호 · 코드 · 와이파이는 다루지 말 것, 그런 답장 묶음은 skip」.
  3. 서버 걸러내기(`containsSecretLike` · `anySecretLike`, `reply-candidates-model.ts`): 조직 비밀 값이 (띄어쓰기 · 하이픈 섞여도) 들어 있거나,
     한 문장에 비밀 낱말(한 · 일 · 영: 비밀번호 · 暗証 · door code · key box …)과 숫자 3자리 넘게 · 가린 자리 · `••` 가 같이 있으면 버린다.
     와이파이 낱말(Wi-Fi · 와이파이 · SSID)도 같은 규칙. 모델이 돌려준 제목 · 질문 · 본문 · 값 · 근거 모두 이 검사를 거친다.
     비밀 낱말 문장 **바로 다음 조각**도 같은 문장으로 본다(「Door code:\n12 34」). 사이의 빈 줄 · 마침표 뒤 줄바꿈은 건너서 본다
     (「Door code:\n\n12 34」 · 「Door code.\n12 34」 · 「暗証番号です。\n0 9 1 2」 — 2026-11-19 3차, ①의 나눠 쓴 숫자 가림도 같음).
  4. **근거 글은 한 번 더 가린다**(`scrubSecretSentences`): 가린 뒤의 답장이라도 비밀처럼 보이는 문장(와이파이 낱말 포함)은 문장째 `[…]` 로 바꿔 저장한다.
  5. **건물 칸 값에 비밀 낱말이 들어 있으면 숫자가 없어도 버린다**(`mentionsSecretWord` — 「비밀번호는 현관 옆에」 같은 값). 와이파이 낱말만은 허용(「와이파이 있어요」).
- 최신이 이긴다: 값이 섞이면 **마지막으로 쓴 날이 늦은 값**이 첫째(미리 골라 둔 값), 최대 2개. 근거에는 날짜를 같이 싣는다(최대 3개, 최신 순).
- 다른 손님 개인 정보는 가린 글로만(이름 · 연락처 · 금액 · 방 번호).
- 「빼기」는 영영 숨김: 다시 찾기는 `pending` 만 바꾼다 — **새 후보를 먼저 넣고, 실행이 성공(`done`)으로 닫힌 뒤에만 예전 `pending` 을 지운다.**
  실패 · 멈춤(stale)이면 이번 실행 후보를 지우고 예전 후보는 그대로 둔다(실패해서 목록이 비는 일 없음). `added` · `dismissed` 는 기억으로 남아 — 문구는 묶음 가운데가
  가까우면(코사인 0.88 이상) 다시 만들지 않고, 건물 칸은 같은 값 지문(언어별 정규화 글)이면 다시 제안하지 않는다. 「되돌리기」(화면 5초 토스트)로 `pending` 으로.
- 「다시 찾기」 버튼으로만 돈다(자동 실행 없음) · 조직마다 동시에 하나 · 한 번 비용 상한 · 한 달 한도 안.
  **한 달 한도는 모든 조직이 같이 쓰는 하나다**(Anthropic · Voyage 키가 하나라서 — 초안 기록 + 후보 실행을 조직 구분 없이 더함).
- 키(`VOYAGE_API_KEY` · `ANTHROPIC_API_KEY`)가 없으면 `available: false` — 화면은 「사용할 수 없음」. 모델 설정은 `ai-config.ts` 그대로(초안과 같은 모델).

- `guest_reply_candidate_run_start(조직, 사람, 이번 달 시작, 한도, 몫)` — 잠금 하나 안에서: 15분 넘은 `running` 은 `failed`(`stale`)로 닫으며 잡아 둔 몫을 0 으로 풀고 →
  진행 중이면 `busy` → 이번 달 합(초안 기록 + 후보 실행) + 몫(2달러)이 한도를 넘으면 `cap` → 아니면 `running` 줄(몫을 비용으로 잡아 둠) + `started`.
  **끝나면(성공 · 실패 모두) 잡아 둔 몫을 실제 쓴 비용으로 바꾼다.** 멈춤으로 닫힌 실행이 늦게 끝나면 상태는 `failed` 로 두고 실제 비용 · 토큰만 적으며,
  그 실행이 만든 후보는 지운다(예전 후보 유지).
- 두 뽑기 안의 동시 호출(`eachLimited`)은 하나가 실패하면 새 호출을 잡지 않고, 돌던 호출이 모두 끝난 뒤에 실패로 넘긴다 — 닫은 뒤에 후보가 들어가거나 비용이 빠지지 않게.
- 알고 두는 것: 한 번 실행은 몫(2달러)을 이미 돌고 있던 호출 몇 개만큼 넘을 수 있다(남은 몫은 호출 전에만 본다).
  함수 시간 초과로 죽은 실행은 끝 정산을 못 해 멈춤 닫기의 0 으로 남는다(실제 쓴 비용이 기록에서 빠짐).
- `guest_reply_assist_cost_since` · `guest_reply_assist_reserve` 가 후보 실행 비용도 더한다(키 하나 · 한도 하나).
- `guest_reply_cluster_stats(조직, 가운데, 거리, 기간 시작)` — 그 묶음 질문 수 · 처음 · 마지막 날(답 없는 질문 포함).
  `guest_reply_cluster_recent(…, 건물, 개수)` — 답 있는 최근 줄. 둘 다 security invoker · `service_role` 만.

### 9-3. 뽑기 흐름 (`src/lib/guest-messages/reply-candidates-server.ts`, server-only)

1. 「다시 찾기」 → `runReplyCandidates()` — 실행 줄을 잡고 응답, 뽑기는 `after()` 에서(화면은 `getReplyCandidates()` 로 끝을 본다).
2. 재료: 최근 12개월(도쿄 날짜 기준) 그 조직 질문 중 최근 1,500개 표본(1,000줄씩 끊어 읽되 끝이 표본 크기를 넘지 않게). 시작할 때의 `pending` 후보 id 를 적어 둔다
   (지우는 건 성공한 뒤). 문구 · 건물 칸 두 뽑기는 함께 돌리고 둘 다 끝난 뒤 한 번에 닫는다(비용은 둘을 더함). 모델에 주는 날짜는 도쿄 날짜.
3. **(b) 문구**: 표본 안에서 가까운 질문끼리 큰 묶음부터(거리 0.3, 표본 안 4개 이상) → 전체 기간 질문 수가 10번 이상인 묶음만 →
   이미 있는 정해 둔 문구와 0.9 이상 비슷하면 건너뜀(0.8 이상이면 「비슷한 문구가 있어요」 표시용 id) → 기억과 가까우면 건너뜀 →
   최근 답장 8개(가린 글)를 5묶음씩 모델에 → 제목 · 대표 질문 · 본문(세 언어, `{guest_name}` 같은 아는 자리 표시만) · 메모. 최대 30개.
4. **(c) 건물 칸**: 건물마다 최근 답장 150개(가린 글, 400자) → 비어 있는 칸만 모델에 → 칸마다 값 후보 + 근거 번호 →
   근거 10개 미만이면 `few`, 값마다 근거 3개 미만은 버림, 같은 값(띄어쓰기 · 구두점 차이)은 합침, 최신 순 2개.
   이미 채운 칸은 `filled`(건너뛴 이유 목록에 남겨 화면이 「n건뿐이라 못 찾음」을 보여 줄 수 있게).
5. 한 번 비용이 몫을 넘을 것 같으면 남은 호출을 하지 않는다. 키 없음 → `unavailable`, 그 밖의 실패 → `failed`.
6. 가짜 모드(`GUEST_AI_FAKE=1`)는 외부 호출 없이 고정 출력 — 시험 · 로컬 화면 확인용.
