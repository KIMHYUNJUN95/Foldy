# 룸 매핑 대조 — Foldy ↔ STAY ARI Manager

> 실측: **2026-09-17** (roomId 단위 전수 비교)
> 상위: [../archive/31-stay-ari-migration-overview.md](../archive/31-stay-ari-migration-overview.md)

STAY ARI Manager 를 이전하면서 **같은 방을 양쪽이 같은 방으로 보는지**를 확인한 기록이다.
가격을 쓰기 시작하면 이 대조가 틀린 만큼 엉뚱한 방의 가격이 바뀐다.

## 비교 대상

| | 저쪽 | 우리 |
| --- | --- | --- |
| 방 목록 | `src/components/BuildingCalendar.jsx` → `BUILDING_ROOMS` (**하드코딩**) | `rooms` 테이블 (Beds24 동기화) |
| 건물 목록 | `src/constants/buildingData.js` | `properties` 테이블 + `room-label-normalization.ts` |
| 활성 판정 | `INACTIVE_MINSTAY_THRESHOLD = 50` | `BEDS24_INACTIVE_MIN_STAY_THRESHOLD = 50` |
| 듀얼 유닛 대표 | `PREFERRED_DUAL_ROOM_IDS` (**하드코딩**) | `status = 'active'` (minStay 로 실시간 판정) |

**이 차이가 핵심이다.** 저쪽은 사람이 적어 둔 표를 믿고, 우리는 Beds24 가 내려주는 `minStay` 를
믿는다. Beds24 에서 유닛이 바뀌면 **우리는 따라가고 저쪽은 안 따라간다.**

## 확정된 결정 (2026-09-17)

### ① 다카다노바바 객실명은 `2`~`9` 로 **그대로 둔다**

같은 roomId 를 저쪽은 `201호`, 우리는 `2` 라고 부른다.

```
513698  저쪽 "201호"  우리 "2"
513699  저쪽 "301호"  우리 "3"
 …                      …
513705  저쪽 "901호"  우리 "9"
```

우리 값은 Beds24 원본이고 **예약 2,265건 전부**가 `2`~`9` 로 들어와 있다.
**사용자 결정: 바꾸지 않는다.** 나중에 「201호로 고쳐야 하는 것 아닌가」가 다시 나오면
이 줄을 보고 멈춰야 한다 — 고치는 것이 아니라 **이미 검토하고 유지하기로 한 것**이다.

### ② 사노는 판매 캘린더에 **넣는다**

- 청소·예약 캘린더는 `isExcludedOperationalProperty` 로 사노를 뺀다 — **현장 운영 기준**이다
- 그런데 사노는 예약 **338건**, `2027-05-03` 까지 잡혀 있는 **파는 건물**이다
- 판매 캘린더에서 빠지면 그 방은 가격을 고칠 방법이 없다
- 저쪽도 캘린더에는 두고 **매출에서만** 뺀다

구현: `getActiveRoomCatalog(..., { includeNonOperationalProperties: true })` +
`ops-calendar.ts` 가 건물 단위 제외를 걸지 않는다.

> **기존 화면은 건드리지 않았다.** 청소·예약 캘린더·대시보드에서 사노는 계속 빠진다.
> 그쪽까지 열어야 하면 별도 결정이 필요하다.

### ③ 가부키초 803호 가격은 `624198` 에 쓴다

| roomId | 저쪽 | 우리 DB |
| --- | --- | --- |
| `648398` | **선호 유닛** | `inactive`, minStay 99, label `K803` |
| `624198` | 보조 | **`active`**, minStay 1, label `803#` |

**두 시스템이 정반대를 가리킨다.** 저쪽 하드코딩이 Beds24 의 유닛 교체를 못 따라간 것으로 보고
**우리 쪽(활성 유닛 = 624198)을 따른다**(사용자 결정).

→ **가격 쓰기를 붙일 때 저쪽 `PREFERRED_DUAL_ROOM_IDS` 를 그대로 옮기지 않는다.**
활성 판정으로 대표 유닛을 고른다. 아라키초A 501호는 양쪽이 `502229` 로 같아 문제 없다.

### ④ 다카다노바바 `401_2`(556719)는 **계속 숨긴다**

우리 DB 에만 있고 `active` 지만 `isExcludedOperationalRoom` 이 숨긴다(예약 13건,
2025-04-15 ~ 2026-06-09). **사용자 결정: 숨김 유지.** 판매 캘린더에서도 숨긴다.

## ⑤ 아라키초A 401호 `515300` — 동기화 버그였다 (2026-09-17)

저쪽 401호는 `440617` + `515300` 듀얼인데 **우리 `rooms` 에는 `440617` 만 있었다.**
사용자 확인: **`515300` 은 Beds24 에 살아 있는 같은 객실이다.** 즉 우리가 놓친 것이다.

### 원인 — 라벨로 맞추던 upsert 가 방을 조용히 덮어썼다

```ts
// 예전 upsertRoom
.upsert({ ... }, { onConflict: "organization_id,room_label" })
```

`rooms` 에는 `UNIQUE (organization_id, room_label)` 이 걸려 있다. Beds24 가 **같은 이름의 방
둘**을 내려주면 두 번째 upsert 가 첫 번째 행을 **UPDATE 해 버린다** — 에러도 없고 `skipped`
에도 안 남아 **방 하나가 증발한다.**

다른 듀얼 유닛이 멀쩡한 이유는 Beds24 가 이름을 구분해 주기 때문이다
(`201` / `201_2`, `501` / `501_2`). **401호만 둘 다 같은 이름**이라 충돌했다.

증거: 두 roomId 모두 `propertyId 176430`(Arakicho A) 소속이고(예약 payload 확인),
22개 중 21개만 남았으며, 잃은 것이 정확히 그 쌍이다.

### 더 위험했던 점

어느 쪽이 행을 차지하는지가 **Beds24 응답 순서에 달려 있었다.** 지금은 `440617` 이지만
순서가 바뀌면 `515300` 이 차지하고, 그때부터 **주 유닛(`440617`, 2027-01-11 까지 예약)으로
들어오는 새 예약이 `(unknown)` 이 된다.**

### 피해

`515300` 으로 들어온 예약 **78건**(확정 66 · 취소 12, 2024-09-05 ~ 2026-03-31)이
`room_label = "(unknown)"` 로 쌓였다(`reservations-backfill.ts` 의 `resolvedRoomLabel || "(unknown)"`).
전체 DB 에서 `(unknown)` 은 이 roomId 하나뿐이다.

그대로 두면 판매 캘린더에서 2024-09 ~ 2026-03 을 열 때 아라키초A 에 **`UNKNOWN` 객실 행**이
하나 더 생기고, 가동률·매출에서 401호 매출 일부가 엉뚱한 방으로 잡힌다.

### 고친 것

`upsertRoom` 의 기준을 **`external_room_id`** 로 바꿨다.

```
① external_room_id 로 기존 행을 찾는다 → 있으면 update (라벨은 유지)
② 없으면 → 라벨이 겹치면 _2, _3 을 붙여 insert
```

- `onConflict` 를 `external_room_id` 로 바꾸지 않은 이유: 그 유니크 인덱스
  (`rooms_beds24_ext_room_id_idx`)가 **부분 인덱스**라 PostgREST 가 충돌 대상으로 추론하지
  못할 수 있다. 명시적으로 조회한다
- 접미사는 **Beds24 가 이미 쓰는 규칙**이다. 표시 계층이 `_N` 을 떼므로 두 유닛은 캘린더에서
  한 행으로 합쳐진다
- 기존 행의 **라벨은 바꾸지 않는다** — 청소 기록·교통비가 라벨로 붙어 있어 Beds24 쪽 이름이
  흔들릴 때마다 따라가면 그 연결이 끊긴다
- 접미사를 받으면 `console.warn` 을 남긴다. 조용히 넘어가면 안 되는 사건이다

회귀 테스트: `src/lib/__tests__/beds24-room-label-candidates.test.ts`

### 실행 결과 (2026-09-16 실측)

방 마스터 동기화를 돌렸다. **아라키초A 21행 → 22행.** `515300` 이 생겼다 —
**라벨 충돌이 원인이었음이 확정됐다.**

```
440617  →  401        active    minStay 2    ← 주 유닛
515300  →  401_2_2    inactive  minStay 99   ← 다른 _2 유닛과 같은 상태
```

`515300` 은 Beds24 에 살아 있지만 **인벤토리상 minStay 99** 라 다른 두 번째 유닛
(`201_2`·`501_2` 도 99)과 똑같이 비활성이다. 즉 **판매하지 않는 유닛**이고, 그 점에서 형제들과
일관된다.

예약 78건의 `room_label` 과 `source_reservation_id` 를 `(unknown)` → `401_2` 로 보정했다.
형제 유닛들이 쓰는 형식 그대로다(`501_2` 468건, `201_2` 31건 …).
**전체 DB 에 `(unknown)` 이 0건 남았다.**

### 왜 `401_2_2` 인가 — 라벨 유니크가 조직 전체이기 때문

Beds24 는 `515300` 을 **`401_2`** 라고 부른다. 그런데 그 라벨은 이미
**다카다노바바 `556719`** 가 쓰고 있었다 — `rooms` 의 유니크는 건물별이 아니라
**조직 전체**(`UNIQUE (organization_id, room_label)`)다. 그래서 동기화가 `_2` 를 한 번 더 붙였다.

저장값은 그대로 두고 **표시 계층에서 뗀다**(`stripArakichoDisplaySuffix` 가 `(?:_\d+)+$` 를
제거 → `401`). 이 파일의 다른 규칙과 같은 방침이다 — 라벨을 바꾸면 청소 기록·예약 매칭이 끊긴다.
회귀 테스트: `room-label-display.test.ts`.

### 같이 터진 사고 — 방 마스터 동기화가 minStay 를 덮어썼다

동기화를 돌린 직후 **비활성 24개가 전부 활성**이 됐다(`inactiveRooms: 0`, 전 객실 minStay 1).

`GET /properties` 의 `roomTypes[].minStay` 는 방의 **기본 설정값**이고, 활성/비활성을 가르는
값은 `GET /inventory/rooms/calendar` 에서 오는 **기간별 값**이다(`inventory-sync.ts`).
방 마스터 동기화가 기본값으로 덮어쓰면서 은퇴 유닛이 전부 되살아났다.

**이건 내 변경이 만든 버그가 아니라 원래 있던 것**이다 — 예전 코드도 같은 필드를 썼다.
동기화를 돌린 적이 없어 드러나지 않았을 뿐이다.

| | |
| --- | --- |
| 복구 | 인벤토리 동기화 재실행 → 91객실 전부 제자리 (아라키초A 11/11) |
| 예방 | `upsertRoom` 이 **기존 방에는 `external_minimum_stay`·`status` 를 쓰지 않는다.** 그 두 필드의 주인은 `inventory-sync` 다. 방 마스터 동기화는 **방의 존재와 소속만** 맞춘다 |

> **방 마스터 동기화를 돌리면 인벤토리 동기화도 함께 돌려라.** 새로 생긴 방은 minStay 가
> 기본값이라 인벤토리가 채워 줘야 실제 활성/비활성이 정해진다.

## 다시 대조해야 할 때

- Beds24 방 마스터 동기화가 방을 새로 만들거나 상태를 바꿨을 때
- 가격 쓰기를 켜기 직전 (대표 유닛이 어긋나면 엉뚱한 방에 쓴다)
- 매출 화면을 만들 때 — 저쪽 `SalesLog` 는 **다이쿄초·사노시·오쿠보A동**을 제외한다.
  우리에겐 그 규칙이 없다. 숫자를 맞추려면 같은 제외를 걸어야 한다 (**아직 미결정**)
