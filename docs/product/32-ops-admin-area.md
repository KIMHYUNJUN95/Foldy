### 판매 캘린더가 지금 보여주는 것

- **예약 · 블락은 실제 데이터다.** 2022년부터 백필한 예약(15,425건)과 `room_blocks` 를 읽는다.
- **가격 · 최소 숙박일도 실제 데이터다** (2026-09-17). `room_daily_rates` 에 12개월치
  **33,306행**(91객실 × 366일)이 들어 있다. 값이 없는 칸은 회색 대시(`–`)로 둔다 —
  **0원이 아니라 「안 판다」는 뜻**이다(비활성 유닛은 애초에 가격이 없다).
- 가로축은 **어제부터 30일**이 기본이고 월간으로 전환할 수 있다. 기존 캘린더의 3개월 제한은
  여기에 없다 → [33](33-calendar-write-features.md) 「뷰 모드 두 가지」.
- 예약 막대는 **체크인 날짜 칸의 가운데에서 체크아웃 날짜 칸의 가운데까지** 그린다. 같은 날
  나가는 예약과 들어오는 예약이 그 칸 가운데에서 만나야 하루에 둘이 보인다.

## 무엇인가

STAY ARI Manager 에서 가져오는 기능(캘린더 쓰기 · 가동률 · 매출 · 자동화)이 **들어가는 곳**.
사무실 직원 소수만 들어가고, 들어온 사람은 그 안의 기능을 **전부** 쓴다.

## 왜 따로 만드는가

### 기존 콘솔에 섞으면 안 되는 이유

**① 성격이 다르다.** Foldy 의 예약 캘린더는 **읽기 전용**이다 — 예약을 보고, 차단을 보고,
객실 상태를 본다. 가져오는 캘린더는 **쓰기**다 — 가격을 바꾸고 재고를 조정하고 예약을 만든다.
같은 화면에 두면 「보러 들어갔다가 고치는」 사고가 난다.

**② 보는 사람이 다르다.** 기존 콘솔은 현장·사무 전원이 본다. 이쪽은 **가격을 만질 수 있는 극소수**다.

**③ 위험이 다르다.** 기존 콘솔에서 잘못 눌러 봐야 우리 DB 가 틀어진다. 이쪽에서 잘못 누르면
**에어비앤비·부킹닷컴에 그대로 나간다.** 되돌릴 수 없는 종류다.

## 진입점

- **사이드바 또는 상단에 메뉴로 노출한다.** 숨기지 않는다 — 쓰는 사람이 찾을 수 있어야 한다.
- **권한이 없으면 메뉴 자체가 보이지 않는다.** Foldy 의 기존 방식 그대로다
  (`admin-shell.tsx` 가 `session.capabilities` 로 내비게이션을 거른다).
- 경로를 직접 쳐서 들어와도 서버에서 막는다. **메뉴 숨김은 UI 편의이지 보안이 아니다.**
- 권한이 없으면 말없이 홈으로 보낸다. **예외 — 예약 바로가기**(`/go/reservation/<id>`, Slack 알림 링크)는 「권한이 없어요」 화면을 보여 준다
  (링크를 누른 사람은 무엇을 열려 했는지 안다). [36](36-automation-control.md) 「예약 바로가기 링크」.

## 권한 — 키 하나로 연다 (확정)

들어오는 사람이 극소수이고, **들어왔으면 그 안의 기능을 전부 쓴다.** 그래서 기능별로 쪼개지
않는다.

```
ops_admin.access   ← 이 키 하나가 영역 전체를 연다
```

기능별로 쪼개는 방안(가격 / 재고 / 예약생성 따로)도 검토했으나 **쓰지 않기로 했다**
(2026-09-16). 쓰는 사람이 사무실 직원 몇 명뿐이라 쪼개 봐야 관리 부담만 늘고, 「가격은 되는데
재고는 안 되는」 상태가 실제 업무에 없다.

**2026-10-20 — 판매 캘린더 「바꾸기」만 뗐다(권한 정리 5-1, 사용자 결정).** `ops_calendar.write` 가 있어야 가격 · 최소숙박 · 차단 · 수기 예약 ·
예약 수정 · 옮기기 · 취소 · 되돌리기 · 대기 가격 보내기를 한다(서버 액션 `requireOpsWriter` · 화면 `canWriteOpsCalendar`). 기본 역할은
`ops_admin.access` 와 같은 대표 · 전무라 **지금 쓰는 사람에게는 달라지는 게 없다** — 나중에 「보기만 할 사람」에게 영역을 열어도 채널로 바로
나가는 쓰기는 잠겨 있게 하려는 것. 없으면 판매 캘린더가 보기 전용(PC: 「수기 예약」 · 「가격 수정」 단추 · 빈칸 `+` · 막대 끌기 · 예약 패널의
수정/옮기기/취소 · 이력의 되돌리기/지금 보내기가 없다. 모바일: 칸을 골라도 가격 · 최소숙박 · 차단 · 예약 만들기 없이 칸 이력만, 예약 시트 단추 없음).
읽기(상세 · 이력 · 빈방 · 매출 요약)는 `ops_admin.access` 그대로. 개인 부여 · 차단 가능(「보되 못 바꾸는 사람」).

```
ops_admin.access     ← 영역에 들어오기 · 보기
ops_calendar.write   ← 판매 캘린더 바꾸기 (기본 대표 · 전무)
```

> **나중에 쪼개야 하면 쪼갤 수 있다.** 권한 체계가 이미 그렇게 설계돼 있다
> (역할 기반 + 개인 지정 부여/차단). 키를 추가하고 정책에 등록하면 된다 —
> [27-permission-override-workflow.md](27-permission-override-workflow.md).

### 누가 받는가

| | |
| --- | --- |
| 기본 부여 | 오너 · 전무 · 개발자 |
| 개인 지정 | 사무실 직원 중 지정된 사람 (사용자 화면에서 직접 부여·회수) |
| 그 외 | 접근 불가. 메뉴도 안 보인다 |

**현장 직원은 역할로는 절대 못 들어온다.** 필요하면 개인 지정으로만 연다. 이 구조는 채용 기능에서
이미 쓰고 있는 방식과 같다.

### 등록 위치

`src/config/capabilities.ts` 레지스트리에 키를 추가하면 **앱·DB·시드 SQL 이 함께 따라온다.**
레지스트리와 DB 정책이 어긋나면 테스트가 잡는다(`capability-registry.test.ts` 의 시드↔레지스트리
대조). 따로 SQL 을 손으로 쓰지 않는다.

## 화면 구성 — 5개의 **별개 메뉴** (2026-09-16 확정)

영역 안은 **나란히 놓인 5개의 독립 화면**이다. 탭이 아니라 각자 메뉴 항목이고, 각자 URL 이 있다.

| 메뉴 | 내용 | 저쪽 원본 | 위험 |
| --- | --- | --- | --- |
| **캘린더** | 가격·최소숙박·재고·블락·예약생성·예약취소 | `BuildingCalendar` | **쓰기** |
| **가동률** | 점유율·객실별 성과·국가별 | `OccupancyRateDashboard` 외 | 읽기 |
| **매출** | 매출·ADR·RevPAR·채널별 | `RevenueDashboard` · `SalesLogDashboard` | 읽기 |
| **전표** | 일별 매출 전표 + 날짜별 메모 | `SalesLog` (`/daily-log`) | 읽기 · 메모 쓰기 |
| **자동화** | 리포트 발송 상태·수동 실행·설정 | 리포트 함수군 | 외부 발송 |

**자동화**(2026-10-06 1차 구현): 화면은 `ops_admin.access` 로 보고, 설정 · 발송 · 담당자 이름은 **`automation.manage`(개인 부여만)** 가 있어야 한다.
Slack 자동화 5종(일일 운영 리포트 · 청소/셋팅 명단 · 취소 · 당일예약 · 실패 알림) — `docs/product/36-automation-control.md`.

같은 묶음에 **룸 링크**(`/admin/ops/room-links`, 2026-10-02)도 있다 — 단 권한은 따로(`room_links.access`). 리스팅 확인은 가격을 만지지 않는 사람도 하기 때문이다. `docs/product/35-room-links.md`.

### 지표를 캘린더 안에 넣지 않는다 (확정)

**가동률·매출·전표는 캘린더의 탭이 아니다.** 캘린더 화면 안에 지표 탭을 만들지 않는다.

**왜.** 캘린더는 **파는 곳**이고 지표는 **본 결과**다. 하는 일도, 보는 주기도, 위험도 다르다 —
캘린더는 한 번 잘못 누르면 채널로 나가고, 지표는 아무리 눌러도 아무 일도 안 난다. 같은 화면에
묶으면 「지표 보러 들어갔다가 가격을 만진다」가 생기고, 화면이 무거워져 **모바일에서 먼저
망가진다**(저쪽 `BuildingCalendar.jsx` 가 11,672줄이 된 경로가 이것이다).

저쪽도 실제로는 `/calendar` · `/occupancy-rate` · `/revenue` · `/daily-log` 로 **이미 갈라져 있다.**
합치는 쪽이 오히려 원본에서 멀어진다.

**모바일에서도 같은 5개를 전부 쓴다.** 축소판이 아니다 — 저쪽 웹의 가장 큰 불만이 「모바일에서
제대로 안 된다」였다. → [31](../archive/31-stay-ari-migration-overview.md) 「모바일이 설계의 출발점이다」

## 기존 화면과의 관계

| | 기존 예약 캘린더 (`/admin/calendar`, `/mobile/calendar`) | 운영 관리자 캘린더 |
| --- | --- | --- |
| 목적 | 오늘 누가 어디 있는지 본다 | 팔 것을 만든다 |
| 권한 | 운영 인원 전반 | `ops_admin.access` 보유자만 |
| Beds24 | 읽기만 | **쓰기** |
| 남기는가 | **그대로 남긴다** | 새로 만든다 |

**기존 캘린더를 대체하지 않는다.** 현장이 보는 화면은 지금 그대로 둔다 — 쓰기 기능이 섞이면
현장에 위험이 옮겨붙는다.

### 기간도 분리한다 (2026-09-16 확정)

기존 캘린더는 **당월 + 2개월**만 읽는다. 그 밖의 달로 넘어가면 「범위 밖」 안내가 뜨고,
모바일은 **조회 자체를 건너뛴다.**

2026-09-16 에 2022년부터의 예약을 백필하면서 「그럼 기존 캘린더도 다 보이느냐」가 나왔는데,
**보이지 않는다** — 데이터가 들어와도 화면이 3개월로 막고 있다.

**그 제한을 푸는 대신, 운영 관리자 캘린더만 넓게 만든다.**

| | 기존 캘린더 | 운영 관리자 캘린더 |
| --- | --- | --- |
| 범위 | 당월 + 2개월 (**그대로**) | **12개월 이상** |
| 보는 사람 | 현장·사무 전원 | 가격·매출을 다루는 극소수 |
| 목적 | 오늘 누가 어디 있나 | 몇 달 앞을 팔 준비 |

**왜 기존 것을 넓히지 않는가.** 현장 직원이 2023년 예약을 볼 일은 거의 없는데, 그것 때문에 매일
쓰는 화면이 무거워진다 — 특히 모바일에서. 3개월 제한은 실수가 아니라 **그 화면의 전제**다.

> 운영 관리자 캘린더가 완성되기 전에 기존 캘린더의 범위가 당장 답답하면, 전면 개방 대신
> **과거 3개월 ~ 미래 6개월** 정도로 넓히는 중간안을 쓸 수 있다. 다리 역할이다.
