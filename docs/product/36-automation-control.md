## 무엇을 하는가

운영 관리자 영역의 **「자동화」 탭**(`/admin/ops/automation`, 지금은 빈 페이지)을 **자동화 관제실**로 만든다.

리포트를 «보내는 곳»이 아니라 **무엇이 · 언제 · 어디로 갔는지 / 안 갔는지 / 왜 안 갔는지를 보고 손대는 곳**이다.
저쪽(STAY ARI Manager)은 이 정보가 Firestore 스냅샷과 Cloud Functions 로그 안에 숨어 있어서
「리포트가 안 왔을 때 알기 어렵다」(34번 「저쪽에서 아쉬웠던 점」)가 그대로 문제였다.

**순서**: Slack 부터. 구글 시트 · Notion 은 같은 틀에 나중에 얹는다.
**연동(실제 Slack 발송)은 나중** — 처음엔 전부 **발송 꺼짐**으로 짓고, 미리보기로 확인한 뒤 켠다.

### 구조

봇 없음. **Incoming Webhook 5개**, 메시지는 mrkdwn 텍스트 한 덩어리(`{ text }`).

```
[스케줄]  06:30 일일 리포트 ──(06:50 재시도: 스냅샷 없을 때만)
          05:15·18:15 Hotelsmart 담당자 미리 수집(18:15 은 다음 날 분)
          06:30 청소 명단 ──(06:50·07:50·08:50 재시도)

            ├ 신규 · 당일 예약          → 당일예약 알림
```

### ① 일일 운영 리포트 (`buildAndSendSlackDailyReport`)

- 대상일: **어제(예약일 기준)**. 수동은 `date=` 또는 `target=today`.
- 금액 = `totalPrice ?? price`(`getBookingAmount`).
- **신규**: 채널 Airbnb · Booking.com 만 · `confirmed` · `bookDate = 대상일` · 금액 > 0 · 다이쿄초 제외.
- **취소**: 같은 두 채널 · `cancelled` · 도쿄 기준 `cancelTime`(없으면 `modified`)의 날짜 = 대상일 · 입실일이 대상일 ±6개월 안.
- **내용**: 전 건물 합계(신규 · 취소 · 매출) → 채널별(에어/부킹) 신규 · 취소 → 입실월별 신규 · 취소 → 건물별(9개 하드코딩:
  아라키초A · 아라키초B · 가부키초 · 오쿠보A동 · 오쿠보B동 · 오쿠보C동 · 다카다노바바 · STAY ARI Apartment Hotel · 사노시,
  건물마다 입실월 내역 · 매출) → 당월 누적(예약일 1일~대상일, 확정건) 건수 · 입실월별.
- **1회 발송**: `slack_report_snapshots/daily_report_{날짜}` 에 신규 · 취소 · 매출 · 당월누적 4개 숫자. 같으면 생략.
- **죽은 코드**: 「변동 재전송」(직전 대비 증감 + 상세 10건)은 `scheduleOutputUpdates` 의 `skipSlack = true` 기본값 때문에 도달하지 않는다.
- 발송 실패 시 3회 재시도(5초 × 회차 대기).

### ② 청소 · 셋팅 명단 (`buildAndSendSlackCleaningReport`)

- 대상일: **오늘**. `confirmed` 중 `departure = 오늘` · `arrival = 오늘`. 다이쿄초 제외.
- **청소 목록** = 오늘 퇴실 객실. 같은 객실 오늘 입실이 있으면 `이름 (인원)`, 없으면 `체크인 X`, 그 뒤 예약이 있으면 `체크인 X (다음 인원)`.
- **셋팅 목록** = 오늘 입실인데 같은 날 퇴실이 없는 객실.
- **담당자** = Hotelsmart(외부 청소 배정 웹, Playwright 헤드리스 로그인 · 수집). 실패하면 당일 캐시 → 지난 발송 스냅샷 →
  없으면 「담당자 미배정」. 이름 깨짐(`??`, `�`) 검사.
- **SKY(STAY ARI Apartment Hotel)는 예외** — 우리 예약이 아니라 **Hotelsmart 화면 자체가 청소 목록 원본**.
- 객실 코드 변환 하드코딩: `AA{번호}` · `AB{번호}` · `K{번호}` · `T{층}` · `sky{번호}`, 건물 순서 · 표시 이름(오쿠보A ↔ B동 교차).
- 1회 발송: 메시지 해시 + 담당자 컨텍스트 스냅샷. 담당자 비면 `sent_partial` → 재시도 때 정정본.
- **정정본**: 오늘 도착 건의 도착일 · 객실 · 상태가 바뀌면 큐(`slack_cleaning_correction_jobs`) → 한 번에 하나 처리.
  아침 명단을 보낸 날만, 담당자는 아침 스냅샷 재사용, 해시 같으면 생략, 머리말 「🔄 청소/셋팅 명단 정정본」.

### ③ 취소 알림 (`sendCancelAlert`)

- 상태가 `cancelled` 로 **바뀌는 순간마다**. 제목은 「🔔 당일 취소 1건」이지만 **기간 · 채널 제한 없이 모든 취소**.
- 건물 · 객실 · 체크인/아웃 · 박수 · 게스트 · 인원(성인/아동) · 플랫폼 · 금액 · 예약ID · 취소 시각(JST).
- **중복 방지 없음** — 웹훅과 정합성 두 경로에서 두 번 갈 수 있다.

### ④ 당일예약 알림 (`sendSameDayBookingAlert`)

- 신규 · `confirmed` · `bookDate = arrival = 오늘` · 금액 > 0 · 다이쿄초 제외 · **채널 무관(수기 포함)**. 형식은 취소 알림과 같다.
- **중복 방지 없음**.

### ⑤ 실패 알림 (`sendSyncAlert`)

`[Sync Alert] 제목` + 줄들. 제목+내용 해시로 15분 억제(`sync_alert_dedupe`). 호출 21곳(Beds24 동기화 · 웹훅 · 시트/Notion 리포트 ·
청소 정정 · Hotelsmart 수집 …).

### 저쪽의 위험 — 옮기면서 고친다

- 일일 리포트 수동 발송 주소(`sendSlackDailyReportManual`) **인증 없음**.
- 취소 · 당일예약 **중복 방지 없음**.
- 건물 목록 · 객실 코드 · 제외 건물(다이쿄초) **하드코딩**.
- 시각이 코드(`onSchedule("30 6 * * *")`)에 박혀 **바꾸려면 재배포**. 재시도도 스케줄을 따로 둔다.
- 실패 알림이 업무 채널로 **대신** 간다.
- 「당일 취소」 문구가 실제 동작과 다르다.

### 발송 켜기/끄기 — 토글 하나 (2026-10-06 사용자 결정)

**드라이런(만들어서 기록만) 단계는 없앤다.** 자동화마다 **발송 토글 하나**(켜짐 · 꺼짐)만 둔다 — 저쪽 프로젝트가 멈춰
이중 발송 위험이 없어졌고, 확인은 미리보기 탭으로 충분하다.

| 상태 | 동작 |
| --- | --- |
| 꺼짐 | 아무것도 안 보낸다(실행 기록도 안 쌓임). 미리보기 · 「지금 보내기」는 그대로 쓸 수 있다 |
| 켜짐 | 시각/사건이 되면 만들어서 Slack 으로 보낸다 |

- 켤 때만 확인 창 한 번: 「켜면 ○○ 이(가) (매일 06:30 에 / 예약이 취소될 때마다) Slack 으로 실제로 나갑니다 · 받는 곳 N곳 · 메시지 N통」.
  끌 때는 바로 꺼진다. 토글은 `automation.manage` 만.
- 목록은 글자 「켜짐」(초록) / 「꺼짐」(회색) — 스위치는 상세 머리의 하나뿐(2026-10-15 화이트 리디자인). 선택된 목록 항목은 옅은 배경만(왼쪽 색 테두리 없음).

### 발송 시각 — 대시보드에서 설정 (2026-10-06 사용자 요구)

시각은 **DB 에 두고 1분 틱이 판단**한다. 바꾸면 배포 없이 다음 틱부터 적용, 오차 1분 이내.

```
설정 탭 → automation_jobs.send_time = '06:30'(도쿄)
1분 틱 → 「지금(도쿄) ≥ 발송 시각」 && 「오늘 성공 기록 없음」 && 「마감 전」 → 실행
```

| 설정 | 예 | 대상 |
| --- | --- | --- |
| 발송 시각 | `06:30` | 시각형(일일 리포트 · 청소 명단) |
| 요일 | 매일 / 평일 / 요일 칩 | 시각형 |
| 재시도 마감 | `09:00` 까지 | 시각형 — 저쪽의 06:50 · 07:50 · 08:50 재시도 스케줄을 대신한다 |

**규칙**

- 오늘 이미 보낸 뒤 시각을 바꾸면 → 오늘은 다시 안 보내고 내일부터.
- 지금보다 이른 시각으로 바꿨고 오늘 아직 안 보냈으면 → 다음 틱에 바로 나간다. 저장 전에 「지금 바로 발송됩니다」 확인.
- 선행 작업(Hotelsmart 담당자 수집 등)은 발송 시각에서 **계산**하고 화면엔 보여 주기만(「담당자 수집 05:30」).
- 관문(예약 데이터)이 막히면 보내지 않고 「관문 막힘 — 사유」를 기록, 마감 전까지 매 틱 다시 본다. 마감까지 실패면 실패 알림.
- 시각 · 상태 · 설정 변경은 누가 언제 무엇을 바꿨는지 **설정 변경 이력**에 남긴다.

### 실행 기반 — 1분 틱

이미 있는 `beds24-tick`(pg_cron 1분 · `202609300004`)과 같은 방식으로 **`automation-tick`** 을 따로 둔다.
pg 함수가 SQL 로 「할 일이 있나」만 보고, 있을 때만 `net.http_post` 로 `/api/automation/tick` 을 부른다
— 할 일이 없으면 Vercel 함수는 한 번도 안 뜬다. GitHub Actions 지연(실측 40분~3시간 40분) 문제가 없다.

### 메시지 언어 — 자동화마다 ko / ja / en 선택 (2026-10-06 사용자 요구)

저쪽은 메시지가 **한국어 하드코딩**이다. 우리는 앱과 같은 3개 언어를 **메시지 본문에도** 적용한다.

- **받는 곳(destination) 단위로 언어를 고른다**(설정 탭) — 자동화 하나에 받는 곳을 여러 개 둘 수 있고, 받는 곳 = **채널 + 언어**.
  기본은 `ko` 하나(저쪽 그대로 → 대조 쉬움). 예: 청소 명단 → 사무실 채널 `ko` + 청소 스태프 채널 `ja`.
- **화면 = 받는 곳마다 언어 체크박스**(2026-10-06 사용자 결정): 설정 탭의 받는 곳 줄에 `한국어 ☑ 日本語 ☐ English ☐` —
  **체크한 언어마다 메시지가 하나씩 간다.** 하나도 체크 안 하면 그 받는 곳은 저장할 수 없다(최소 1개). 바꾸는 것은 `automation.manage` 만.
  ```
  받는 곳                 언어
  #청소-사무실             [x] 한국어  [ ] 日本語  [ ] English
  #cleaning-staff          [ ] 한국어  [x] 日本語  [x] English   → 이 채널엔 2통
  ```
- **여러 언어는 메시지를 나눠 보낸다**(2026-10-06 사용자 결정 — 한 메시지에 두 언어는 가독성이 나쁘다). 같은 채널에 `ko` · `ja` 둘을 걸면
  두 메시지로 따로 간다. 받는 곳마다 실행 기록 · 중복 방지 · 재시도가 **따로** 돈다(한쪽 실패가 다른 쪽을 막지 않는다).
- **번역 대상**: 제목 · 항목 이름(신규 예약 · 취소 · 매출 · 당월 누적 · 셋팅해야 하는 객실 · 체크인 X · 담당자 미배정 · 정정본 머리말 …) ·
  월 표기(`10월` / `10月` / `Oct`) · 날짜 · 요일 · 인원(`성인 2명` / `大人2名` / `2 adults`) · 채널 이름 · 실패 사유 문구.
- **건물 이름** = 우리 `properties.display_name_{ko,ja,en}`. 비어 있으면 기본 이름. 객실 코드(`AA201` · `K302` …)는 언어와 무관.
- **바꾸지 않는 것**: 게스트 이름 · 예약 번호 · 금액(`¥` · 천 단위 쉼표는 세 언어 공통).
- **문구 위치**: 공용 사전(`src/lib/i18n.ts`)에 **`automationMessages`** 네임스페이스로 ko/ja/en 을 함께 넣는다(CLAUDE.md 다국어 규칙).
  메시지는 서버에서만 만들어지므로 함수형 문구도 가능하지만, 관제실 미리보기와 같이 쓰려면 `{name}` 자리표시 문자열 + `.replace()` 로 통일.
- **미리보기 언어 전환** — 미리보기에서 언어 칩을 눌러 세 언어 메시지를 바로 비교. 설정을 바꾸지 않고 보기만.
- **대조(P4)는 `ko` 기준** — 저쪽 메시지가 한국어라서. 대조가 끝나 전환한 뒤에 다른 언어로 바꾸는 순서를 권장.
- **누락 방지 테스트** — 세 언어 키가 모두 있는지 검사하는 테스트(기존 `dictionary-serializable.test.ts` 처럼). 빠진 키 때문에 메시지가 깨지면 안 된다.
- **실행 기록에 언어 저장**(`automation_runs.locale`) — 어떤 언어로 나갔는지 남긴다.
- 화면 문구(관제실 자체)는 이와 별개로 **보는 사람의 언어**(`preferredLanguage`)를 따른다.

### 청소 명단 담당자 — 대시보드 수기 입력 (2026-10-06 사용자 결정)

Hotelsmart 자동 수집은 약관(제10조 10호) 때문에 하지 않는다. **청소 · 셋팅 명단은 담당자 이름 없이** 우리 예약만으로 보낸다.
**예외**: 관제실에서 사람이 명단에 이름을 넣으면 **넣은 대로** 명단에 붙어 나간다.

- **어디서**: 관제실 → 「청소 · 셋팅 명단」 → 새 탭 **「담당자」**. 날짜(`AdminDatePicker`, 기본 오늘 · 내일도 미리 입력 가능)를 고르면
  그날 명단에 오를 객실이 건물 순서대로 나오고, 객실마다 이름 칸 하나.
  ```
  2026-10-07 (화)                         청소 12 · 셋팅 3
  아라키초A
    AA201  다나카 (2)        [ 김OO          ]
    AA302  체크인 X (3)      [               ]
  셋팅해야 하는 객실
    K302   스미스 (4)        [ 이OO, 박OO    ]
  ```
- **메시지**: 이름이 있는 객실만 `*AA201* | 다나카 (2) | 김OO` 처럼 붙는다. **이름이 없으면 아무것도 안 붙는다**
  (저쪽의 「담당자 미배정」 표시 · 미배정 때문에 생기던 부분 발송/재시도 · 정정본 로직은 전부 빠진다).
  이름은 번역하지 않는다(체크한 언어 모두에 같은 이름).
- **언제 반영되나**
  - 발송 전에 넣은 이름 → 그날 아침 명단에 들어간다.
  - **발송 뒤에 이름을 넣거나 바꾸면** → 자동으로 다시 보내지 않고, 「담당자」 탭에 「발송 뒤 바뀜 N곳」 표시 + **「정정본 보내기」** 버튼
    (타이핑할 때마다 정정본이 나가는 것을 막는다). 예약 변경으로 생기는 정정본(C4)에는 그 시점의 이름이 들어간다.
- **명단에서 빠진 객실의 이름**(예약이 취소돼 명단에서 사라짐)은 지우지 않고 「명단에 없음」으로 흐리게 남긴다 — 다시 생기면 그대로 쓴다.
- **입력 편의**: 이전에 쓴 이름 자동완성 · 여러 명은 쉼표.
- **권한**: 입력 · 정정본 보내기 = `automation.manage`(설정 · 발송과 같은 키). 일상 입력을 다른 직원에게 맡겨야 하면 그때 키를 나눈다.
- **기록**: 누가 언제 어떤 객실 이름을 바꿨는지 설정 변경 이력(`automation_setting_logs`)에 함께 남긴다.
- **키**: 날짜 × **운영 객실 키**(`buildRoomKey` — 청소 화면과 같은 키). 객실 코드(`AA201` …)는 표시용으로만 만든다(저쪽처럼 코드 문자열로 매칭하지 않는다).
- **나중에**: Hotelsmart 에서 서면 허락(K1)을 받거나 다른 길(K2 · K3)이 생기면 이 칸을 자동으로 채우는 쪽으로 붙인다 — 수기 입력이 있으면 수기가 이긴다.

  건드리지 않음). 웹훅이든 증분 정합성이든 예약 표가 바뀌면 1분 안에 잡히고, `dedupe_key`(자동화 · 예약 · 받는 곳 · 언어)가 두 번 막는다.
  켤 때 커서를 「지금」으로 — 켜기 전 사건은 안 보낸다. 취소는 취소 시각이 24시간 안인 것만.
- **받는 곳 표 = 채널 행 × 언어 체크박스.** 환경변수로 찾은 채널이 전부 행으로 나오고, 언어를 하나라도 체크하면 받는 곳이 된다(「받는 곳 추가」
  드롭다운 없음).
- **「저쪽과 대조」 탭은 넣지 않았다** — 저쪽 프로젝트가 멈춰 새 메시지가 없다. 대조는 Slack 채널에 남은 저쪽 지난 메시지와 미리보기(같은 날짜)를
  눈으로 본다.
- 정시 발송 중복 방지 = 「줄을 먼저 잡고 보낸다」(`dedupe_key` 유일 인덱스 → 두 틱이 겹쳐도 한 통). 수동 발송은 중복 방지 없음.

### 폰 가독성 — 알림 · 일일 리포트 (2026-10-07 사용자 요구)

Slack 은 폰에서 주로 본다. `|` 로 이어 붙인 긴 줄 · 그대로 드러난 긴 주소 · 건물 한 줄에 다 넣은 일일 리포트가 폰에서 여러 번 꺾였다. **청소 명단은
그대로 둔다**(사용자 — 현장이 익숙한 형식). 세 언어 모두 같은 구조, 일본어도 한 줄이 넘치지 않게 짧게 나누고 목록은 「、」.

```
🔔 *취소* · 아라키초B 201                       🔔 *キャンセル* · 荒木町B 201
*11/5(목) → 11/7(토)* · 2박 · 4명(아동 1)        *11/5(木) → 11/7(土)* · 2泊 · 4名（子ども1）
Michelle Ng · Booking                          Michelle Ng · Booking
*¥0* · 예약 94244398                            *¥0* · 予約 94244398
취소 10/7(수) 13:09                             キャンセル 10/7(水) 13:09
Foldy 에서 열기  ← 링크 글자만                 Foldy で開く
```

- 첫 줄 = 무슨 일 · 어느 방(폰 알림 미리보기에도 이 줄). 날짜는 요일까지, 올해가 아니면 연도(`2027/2/4(목)`), 당일예약은 「오늘」.
- 인원 = 합계(아동이 있으면 괄호). 링크는 Slack 링크 문법 `<주소|Foldy 에서 열기>` — 긴 주소가 안 보인다.

```
📊 *일일 운영 리포트 · 10/6(화)*

■ 전일 실적 (전 건물 합계)
신규 *22건* · 취소 *13건*
매출 *¥4,786,364*

■ 건물별 실적
*가부키초*  *¥211,257*

　취소 2건 · 1월 1건, 12월 1건

```

### 취소 금액 — 얼마가 빠졌나 (2026-10-07 사용자 요구)

Beds24 는 예약이 취소되면 `price` 를 **0** 으로 비운다 — 저쪽도 우리도 취소 알림이 늘 `¥0` 이었다. 「실제로 얼마가 빠져나갔는지」가 중요하다(사용자).

**원래 금액을 정하는 순서**(`originalAmountOf`, `reservation-fields.ts`)

1. 지금 금액이 0 보다 크면 그대로(수기 예약은 취소돼도 금액이 남는다).
2. **DB 가 기억한 마지막 금액** `reservations.last_known_amount` — 트리거(`reservations_keep_last_known_amount`, 마이그레이션 `202610070003`,
   운영 적용 2026-10-07 14:12)가 예약 행이 바뀔 때 새 금액이 0 이하이면 직전 금액을 남긴다. Beds24 동기화 코드는 손대지 않았다 — 그 코드는 이 컬럼을
   모른다. 기존 행은 일괄로 채우지 않았다(12,000건 넘게 `updated_at` 이 흔들린다) — 취소되는 순간 직전 행의 금액을 잡으므로 필요 없다.
3. **요금 내역** `rateDescription`(Beds24 가 취소 뒤에도 남김): Booking.com = 날짜 줄 `JPY` 합(2026-06 이후 확정 1,174건 중 1,166건 ±10엔, 예약 뒤 연장된 0.7% 는
   적게 나옴), Airbnb = `Base Price` + `Cleaning fee`(1,296건 전부 일치). 단 Airbnb 취소의 약 28% 는 내역까지 `Base Price 0` 으로 와서 2번이 필요하다.
4. 모두 없으면 「확인 불가」 — 0 으로 찍지 않는다.

### 발송 상태 — 보내는 중 · 정정본 판정 (2026-10-19)

한 통 = `automation_runs` 한 줄의 상태 기계: **잡음**(`status=failed`, `reason=sending`, 키 쥠) → 보냄(`sent`) / 실패(키를 `<키>#failed#<id>` 로 놓음)
/ 5분 넘게 「보내는 중」이면 틱이 **중단됨**(`interrupted`, 키를 놓음 — `releaseStuckClaims`, 리스 만료). 키를 쥐는 발송은 틱(최대 60초) 안에서만
일어나므로 5분 넘은 「보내는 중」은 죽은 함수의 것이다.

- **정시 발송이 「보내는 중」 줄에 막혀 오늘을 끝내던 것**(고침) — 발송 도중 함수가 죽으면 다음 재시도 틱에서 그 한 통의 키가 아직 잡혀 있어
  「중복」으로 세고 보낸 0 · 실패 0 → 「완료」(`last_done_on = 오늘`)가 됐다. 그 한 통은 끝내 안 나갔다. 이제 「진행 중」으로 세어 마감 전이면
  5분 뒤 다시 보고(`isScheduledRunDone`), 그사이 리스가 만료돼 키가 풀리면 다시 보낸다.
- **정정본 · 변동 재전송 판정 = 받는 곳 × 언어마다 「그곳에 마지막으로 보낸 내용과 다른가」**(`planFollowUpTargets`, `src/lib/automation/delivery-state.ts`).
  - 중복 방지 키 꼬리 = `correction:<그곳에 마지막으로 보낸 줄 id>:<지문>`(일일 리포트는 `resend:…`). 예전 `correction:<지문>` 은 명단이
    A → B → A → B 로 바뀌면 두 번째 B 가 첫 B 의 키에 막혀 안 나갔다. 직전에 보낸 줄이 바뀌므로 매번 새 키, 같은 판정이 두 번 돌면 같은 키라 한 통.
  - 한 곳만 실패했으면 그곳만 다시 받는다(예전엔 그날 가장 최근에 보낸 한 줄과 비교해, 한 채널이 받으면 실패한 다른 채널은 「같음」으로 빠졌다).
  - 오늘 아무것도 못 받은 곳은 다른 곳에 정정본이 나갈 때만 같이 받는다.
- **중복 발송 근거**: 모든 자동 발송은 `(organization_id, dedupe_key)` 유일 인덱스로 줄을 먼저 잡는다. 같은 키는 한 줄만 「보내는 중/보냄」일 수 있고,
  키가 풀리는 것은 실패 · 리스 만료 때뿐이다. 남는 틈 하나 — Slack 이 받은 직후 결과를 적기 전에 함수가 죽으면 5분 뒤 한 번 더 나갈 수 있다
  (Slack 웹훅에 멱등 키가 없어 「적어도 한 번」을 고른 것 — 안 나가는 쪽이 현장에 더 위험).
